# GLES 3.1 shader patches: status and integrator list (2026-11-12)

Generated by the GLES backend build (`core/engine/hal/gles/gles.cmake`): glslc (SPIR-V) -> `dapple_shaderc` (SPIRV-Cross, ESSL 310) -> lint
with `glslc -std=310es`. The lint is what found the first rule violation below; the manifest field `esViolations` lists the rest.

## 1. Applied: read-write rgba16f images (ES 3.1 allows read-write storage images only for r32f / r32i / r32ui)

`nr_luma.comp`, `nr_chroma.comp`, `dehaze_apply.comp`, `detail.comp` declared `layout(binding = 1, rgba16f) uniform image2D uD;` and did
`imageLoad(uD, p)` + `imageStore(uD, p, ...)`. Patch (in the shader files, guarded by `#ifdef ES_PINGPONG`, so the Vulkan variants are unchanged: the SPIR-V of the four
shaders is byte-identical to the one built from the pre-patch sources of git HEAD):

```glsl
#ifdef ES_PINGPONG
layout(binding = 1, rgba16f) uniform writeonly image2D uD;
layout(binding = N) uniform sampler2D uDin;      // N = first free binding of the shader (4, 4, 5, 6)
#define LOAD_D(p) texelFetch(uDin, (p), 0)
#else
layout(binding = 1, rgba16f) uniform image2D uD;
#define LOAD_D(p) imageLoad(uD, (p))
#endif
```

* GLES shader list (`hal/gles/shader_list.cmake`): these four entries carry `ES_PINGPONG=1` and a signature with one extra trailing `S`
  (`ISIS`, `ISIS`, `ISBIS`, `ISSSIS`). The shader tool gets `--pingpong`, which sets a flag in the table entry.
* Callers keep the Vulkan signature (`ISI` ...): the GLES device accepts the shorter signature for flagged programs and binds the texture
  of the first image slot ALSO to the trailing sampler. This is legal because each invocation reads only its own pixel of `uD` before
  writing it (verified in the four shaders: one `LOAD_D(p)` per invocation, `p` = the invocation's own pixel) and the previous dispatch
  ended with a texture-fetch barrier. No scratch image, no extra copy, the executor and the node record functions are unchanged.
* Verified: `gles_gpu_parity_angle_*` (whole-frame parity incl. NR luma / chroma, dehaze, clarity/texture/sharpen = `detail`) pass on ANGLE
  Vulkan (RTX 4060 Ti) and ANGLE SwiftShader, mean dE2000 <= 0.073, max <= 1.9 against the CPU reference.
* When the planner implements real ping-pong (docs 6.4): drop the aliasing in `GlesDev::exec` (`aliasRead`), give the kernels a separate
  output binding, keep `ES_PINGPONG`.

The Vulkan engineer's files were not touched. The shaders had not changed for > 15 minutes when this was applied (nr_*, dehaze_apply,
detail last written 10:57; the only newer shader at that time was the new `boxscan.comp`, which already complies).

## 2. Applied (GPU executor engineer, 2026-11-12): workgroup size via spec constants (<= 128 invocations)

Every 2D kernel used `local_size 16x16 = 256` (`reduce`: 256), which ES 3.1 does not guarantee (128). Now the shape is a specialisation
constant pair and the node record functions compute the group counts from it:

```glsl
layout(local_size_x = 16, local_size_y = 16, local_size_x_id = 16, local_size_y_id = 17) in;   // convert dehaze_apply detail down gf_ab
                                                                                              // nr_chroma nr_luma point resize film_{grain,mix,point,post}
layout(local_size_x = 256, local_size_x_id = 18) in;                                          // reduce
layout(constant_id = 19) const int WG = 256;                                                  // reduce: the same number as a value
```

* Defaults are the old shapes, so a caller that passes nothing (the GLES self-test, tools) gets 16 x 16 / 256 and the Vulkan SPIR-V behaves as
  before. The generated ESSL carries `SPIRV_CROSS_CONSTANT_ID_16/17/18/19` macros with those defaults and the HAL splices the caller's values.
  (`gl_WorkGroupSize` cannot be used for `WG`: SPIRV-Cross emits the constant before the layout line, which ESSL rejects. Hence the second
  constant, id 19.)
* `GpuRecorder` (`nodes/gpu_common.{h,cpp}`) owns the shape: `workgroupShape(caps)` = 16 x (inv/16) with `inv` = min(256,
  `maxWorkgroupInvocations`) rounded down to a power of two (16 x 16 on every device measured, 16 x 8 for 128; 16 x 4 for 64 by construction, not run);
  `pl()` adds spec ids 16 / 17 / 18 / 19 to every pipeline (a shader that does not declare an id ignores it); record functions use
  `r.gx(w)` / `r.gy(h)` instead of `cdiv(w, 16)`, `recordDehazeAnalysis` sizes the reduction as `cdiv(n, rwg * 16)` groups. `sepconv`
  keeps its own spec constants: 16 x 16 becomes 16 x `ly`, the 64 x 4 variant `min(64, rwg / 4)` x 4 (the shared tile is sized for the
  worst case). `boxscan` is 64 x 2 / 32 x 4 = 128 already.
* Film shaders (`film_grain/mix/point/post`, `film_gpu.cpp` dispatches) got the same mechanical change.
* Env `DAPPLE_GPU_WG=<n>` forces the invocation budget (tests: `DAPPLE_GPU_WG=128` runs the 16 x 8 / reduce 128 shapes on any device);
  the device text of `dapple_gpu_status_json` / `dapple_gpu_tests` prints `workgroup 16x8 (reduce 128)`.
* Verified (desktop): Vulkan RTX 4060 Ti and SwiftShader unchanged vs the 16 x 16 build (every row of the parity table and every pass count
  identical; tiled seams 0 differing pixels); GLES on ANGLE (Vulkan and SwiftShader backends) full `dapple_gpu_tests` and the
  `DAPPLE_GPU_WG=128` stage run (`gles_gpu_parity_angle_*_wg128`) pass with the same dE2000 budgets (mean <= 0.073). Not verified: a real
  device that reports 128 (none measured so far: ANGLE 1024 / 256, emulator 1024).
* `reduce` with a smaller group sums the colour in a different order: the airlight of a 128-group run can differ from the 256 run in the last float bits.

## 3. Other findings of the first GLES runs (device-side fixes already in `gles_device.cpp`)

* `Upload` buffers: the Vulkan backend is host-coherent, callers write through `map()` without `flush()`. GLES keeps a host shadow, so
  the device re-sends every `Upload` buffer a command list reads (TODO: range tracking for the 24 MB staging chunks).
* ANGLE (Vulkan) returns `GL_INVALID_VALUE` from `glCopyBufferSubData` when the source was just written by `glBufferSubData`; buffer ->
  buffer copies therefore run as a small compute pass (word copy), and host-shadow sources use `glBufferSubData` directly.
* `copyImage` used `glUniform4i` on an `ivec2` (INVALID_OPERATION) - fixed. The old symptom: tiled export seams all differ.
* `caps.deviceLocalBytes` is unknowable on GLES: estimated as half of host RAM clamped to 1..4 GiB (resident-source limit in the executor).
* ES 3.1 is not available on the default `swiftshader_indirect` emulator mode ("max version 3.0"): the GLES backend rejects it cleanly
  (`eglCreateContext(ES 3.1) failed`); use `EMU_GPU=host` (translator over the host GL, ES 3.1).
