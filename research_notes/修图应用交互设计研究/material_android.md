# Material 3 / M3 Expressive and Android platform UX for "Dapple" (Flutter, Android-first on foldable, light photo-editing app)

Research date: 2026-11-11. Several m3.material.io pages (window-size-classes, slider specs) returned 404 or no values through the fetch tool, and m3.material.io is JS-rendered. Material token numbers (type scale, shape radii, spring stiffness/damping, slider dimensions) are therefore NOT cited here and are listed under Gaps. Everything marked "Inference" is my reasoning, not a sourced fact.

## 1. M3 foundations (color, type, shape, elevation, motion, targets, contrast) and whether a photo app should use dynamic color

### Takeaway
I could verify only the accessibility floor: 48dp touch targets and 4.5:1 text / 3:1 non-text contrast. I could not retrieve the M3 color/type/shape/motion token tables. For a photo editor the safe stance is a fixed, neutral, brand-controlled light scheme rather than wallpaper-derived dynamic color, because UI chrome tint contaminates color judgment (inference, below).

### Cited Findings
- Android accessibility guidance: text needs at least 4.5:1 contrast against its background, and 3:1 between surfaces and non-text elements such as icons. Large text (18pt+, or bold 14pt+) may use 3:1. — [Android accessibility design](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility)
- Interactive elements should be at least 48dp x 48dp. A visible element can be smaller if padding brings the tappable area to 48dp, and Compose enlarges smaller clickables automatically. — [Android accessibility design](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility)
- Edge-to-edge system bars: system icon colors adapt to the light/dark theme, and `isAppearanceLightStatusBars` can be set manually so icons contrast with your app background. — [Edge-to-edge (views)](https://developer.android.com/develop/ui/views/layout/edge-to-edge)
- The Flutter team froze the in-framework Material and Cupertino libraries in August 2026 and moved them to standalone packages `material_ui` and `cupertino_ui` (v1.0.0, semver, independent release schedule). The team says official M3 Expressive and Liquid Glass implementations are "already underway", with no dates. — [Flutter blog, 2026-09-09](https://flutter.dev/blog/decoupling-material-cupertino)

### Inferences
- Dynamic color (wallpaper-derived tonal palettes) would shift the tint of every surface and slider track. For a tool whose job is judging color and tone in photos, a fixed neutral light scheme (near-neutral surfaces, a single accent) is preferable. Offer dynamic color only as an optional setting, if at all. This is a judgment call, not a Material rule.
- Photo canvas backdrop: keep the surround neutral gray or white and never tinted. On a light UI, use a neutral mid-light gray behind the photo so highlights remain readable.
- Every custom (non-token) color must be checked against the 4.5:1 / 3:1 thresholds above.

### Gaps
- M3 type scale values, shape corner tokens, elevation levels, and the M3 Expressive spring tokens (spatial/effects, fast/default/slow stiffness and damping) were not retrievable from m3.material.io. Third-party Flutter packages reference tokens named `expressiveSpatialFast` / `standardEffectsFast` but these are not official values. Fetch m3.material.io/styles/motion or the Compose `MotionScheme` source before hard-coding any value.
- Official Material 3 wording on contrast of generated tonal palettes was not retrieved.

## 2. Components: nav bar vs rail, floating toolbar, FAB, sheets, sliders, chips, selection mode, snackbar undo, progress

### Takeaway
Window width decides navigation: bottom navigation bar under 600dp, rail at 600dp and up. Material 3 Expressive adds floating toolbars (horizontal and vertical) and button groups that suit an editing tool strip. Slider and selection-mode component dimensions could not be verified.

### Cited Findings
- Flutter's adaptive docs cite Material guidance: bottom navigation bar for windows under 600 logical pixels wide, navigation rail at 600 or more; a `NavigationBar` and `NavigationRail` can share one destination list. — [Flutter adaptive design](https://docs.flutter.dev/ui/adaptive-responsive/general)
- Compose Material3 reference lists `HorizontalFloatingToolbar` and `VerticalFloatingToolbar` (Expressive components); the floating toolbar can control a FAB; `ButtonGroupScope` provides weight and animated width for children. — [Compose Material3 package summary](https://developer.android.com/reference/kotlin/androidx/compose/material3/package-summary?hl=es); [VerticalFloatingToolbar](https://developer.android.com/reference/kotlin/androidx/compose/material3/VerticalFloatingToolbar.composable?authuser=3). Secondary summary: Android 16 / M3E announced 15 new or updated components including app bars and button groups — [ProAndroidDev](https://proandroiddev.com/android-16-x-material-3-e-biggest-ui-change-yet-updates-for-android-jetpack-compose-and-flutter-35d6b53a5242). Secondary sources disagree on which Compose Material3 version is stable for Expressive (1.4 alpha vs 1.5 alpha mentioned); unverified.
- Material components in views automatically handle insets: `BottomAppBar`, `BottomNavigationView`, `NavigationRailView`, `NavigationView`; `AppBarLayout` does not. — [Edge-to-edge (views)](https://developer.android.com/develop/ui/views/layout/edge-to-edge)
- Google Photos (Android) editor redesign: Auto tab with Enhance / Dynamic / AI Enhance; tap or circle an image region to get suggested tools; value sliders redesigned as pill shapes with open/close animation; tap-and-hold shows the original. Users criticized having to tap in and out of sliders to switch between them and called the UI cluttered. — [9to5Google redesign](https://9to5google.com/2025/09/05/google-photos-editor-redesign-android/); [Android Central criticism](https://www.androidcentral.com/apps-software/users-dreading-google-photos-less-functional-editor-updates-report); tap-and-hold compare is from a single-feature walkthrough per [search summary](https://9to5google.com/2025/08/08/google-photos-editor-redesign-tips/) so treat as indicative, not a general rule.

### Inferences
- Dapple's main surfaces: (a) Library/import grid, (b) review/edit canvas, (c) share/export. Navigation needs few destinations (e.g. Library, Looks, Settings), so a NavigationBar on compact and a rail on medium and up fits, but the review/edit screen should be a full-screen destination with no bottom nav (immersion, thumb reach).
- Use a floating toolbar (or a plain bottom row with button group) for edit tool switching; keep 1 to 3 primary sliders always visible rather than the Google Photos pattern of tap-in/tap-out, which users criticized. This directly serves "quick slider tweaks".
- Multi-select: long-press to enter selection mode, contextual top bar showing "N selected" plus share/save actions; a snackbar with Undo for destructive actions (reject/delete). Progress: determinate linear indicator for batch develop/export, with count text ("12/48").
- Compare: press-and-hold on the photo to show original, matching the Google Photos precedent and iOS Photos (HIG-aligned).

### Gaps
- M3 slider spec numbers (track height, handle size, touch target, XS-XL Expressive sizes) — the page fetched listed topics but no values.
- M3 specs for chips, segmented buttons, snackbar duration, bottom sheet heights, selection-mode grid behavior were not retrieved.

## 3. Large screens and foldables: window size classes, canonical layouts, postures, continuity, OPPO Find N5

### Takeaway
Use window size classes (width first), not device checks. The Find N5 inner screen is near-square, so expect expanded or near-expanded width and compact-ish height patterns; design for list-detail / supporting pane and preserve state through fold/unfold. I found no OPPO/ColorOS developer guideline for foldable adaptation.

### Cited Findings
- Android window size classes: Compact width <600dp; Medium 600 to <840; Expanded 840 to <1200; Large 1200 to <1600; Extra-large >=1600. Height: Compact <480; Medium 480 to <900; Expanded >=900. "Most large unfolded inner displays in portrait" are medium; in landscape at least expanded. — [Use window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
- Flutter lists the same M3 breakpoints (compact <600, medium 600-839, expanded 840-1199, large 1200-1599, extra-large >=1600). — [Flutter adaptive design](https://docs.flutter.dev/ui/adaptive-responsive/general)
- Window size class can change during app lifetime (rotation, multi-window, fold/unfold); do not use isTablet-style logic. Open flippables in landscape may have medium width but compact height, where two-pane layouts are impractical. — [Use window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
- Hoist state so it survives layout changes (e.g. fold/unfold); always pass enough data for any display size; use `LayoutBuilder` / `BoxWithConstraints`-type local measurement for reusable components, and window metrics only for app-level layout. — [Support different display sizes](https://developer.android.com/develop/ui/compose/layouts/adaptive/support-different-display-sizes)
- Material canonical layout reference: list-detail (linked from the doc) — [m3 list-detail](https://m3.material.io/foundations/layout/canonical-layouts/list-detail) (page not retrieved; link only).
- Android 16 (targetSdk 36): orientation, resizability, and aspect-ratio restrictions are ignored on displays with smallest width >=600dp (games and user-opted-in exempt); temporary opt-out exists via `PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` but will not apply at API 37. — [Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16)
- Flutter: locking orientation with `setPreferredOrientations` causes portrait compatibility mode/letterboxing on foldable unfold and `MediaQuery` never sees the larger size; support all orientations. For grids use `SliverGridDelegateWithMaxCrossAxisExtent` or compute columns from window width via `MediaQuery.sizeOf`. — [Flutter large screens](https://docs.flutter.dev/ui/adaptive-responsive/large-screens)
- Flutter: `MediaQuery.sizeOf(context)` for app-window decisions, `LayoutBuilder` for widget-level decisions. — [Flutter adaptive design](https://docs.flutter.dev/ui/adaptive-responsive/general)
- Find N5 (official specs): inner 8.12 in, 2480 x 2248 px QXGA+; cover 6.62 in, 2616 x 1140 px FHD+; both up to 120Hz. — [OPPO Find N5 specs](https://www.oppo.com/en/smartphones/series-find-n/find-n5/specs)
- Find N5 dimensions: unfolded 160.9 x 145.6 x 4.2 mm, folded 160.9 x 74.4 x 8.9 mm, 229 g; ~412 ppi inner, ~431 ppi cover. — [GSMArena](https://www.gsmarena.com/oppo_find_n5-13659.php); [TechRadar](https://www.techradar.com/phones/oppo-phones/oppo-find-n5-review); ppi from [The Mobile Indian](https://themobileindian.com/product-finder/product/oppo-find-n5)
- Aspect ratios disagree across sources: cover ~20.7:9 (Digital Trends, gsmchoice) vs 20:9 (TechBuz); inner ~9.9:9 (TechRadar). Pixel math from official specs gives 2616/1140 = 2.29 (cover, about 20.6:9) and 2480/2248 = 1.10 (inner, about 9.9:9).
- Find N5 ships ColorOS 15 on Android 15; inner display supports three-app full-screen multitasking ("Boundless View") and split screen / floating windows launched from a three-dot menu at the top of an app. — [PhoneArena](https://phonearena.com/news/worlds-thinnest-foldable-isnt-just-about-looks-its-got-brains-too_id167796); [OPPO newsroom](https://www.oppo.com/en/newsroom/stories/find-n5-coloros-ai-productivity/)
- Android foldable guidance: Tier 2 (adaptive optimized) or Tier 1 (adaptive differentiated) quality guidelines should give a good experience on trifolds/landscape foldables; judge orientation by the app's actual area. — [Android trifolds and landscape foldables](https://developer.android.com/develop/adaptive-apps/guides/foldables/trifolds-and-landscape-foldables?hl=zh-tw)

### Inferences
- Inner screen is nearly square (about 1.10:1), so portrait/landscape distinction is weak. With typical Android densities (~420 to 480 dpi) the inner display is likely 700 to 880dp per side, i.e. around the medium/expanded boundary at 840dp (my arithmetic from px and ppi, not a published figure). The cover screen, at around 380 to 420dp wide, is compact. MEASURE on a real device (log `MediaQuery.sizeOf` and `devicePixelRatio`) before fixing breakpoints.
- Because the inner screen can land either side of 840dp, build the layout from LayoutBuilder/width thresholds with a hysteresis-free, continuous design (grid columns from max cross-axis extent) rather than one hard two-state switch.
- Recommended layouts: Library = adaptive grid (cover) -> grid + preview/detail pane (inner). Edit = photo large on one side, sliders/tool panel on the other on wide windows (supporting pane); bottom tool area on compact. On wide width, put sliders in a side panel so the photo is never covered by a bottom sheet.
- Continuity: keep selection set, current photo, zoom/pan, and slider state in app-level state so folding/unfolding (activity/config change) does not reset editing; keep decoded previews cached across the transition.
- Tabletop-posture handling (half-fold, content top / controls bottom) is a nice-to-have; Flutter exposes hinge info through `MediaQuery.displayFeatures` (from my general knowledge, not verified in fetched docs). Low priority for v1.

### Gaps
- No OPPO Open Platform / ColorOS foldable design guidelines found (multiple searches); only consumer-level feature descriptions of Boundless View and split screen.
- Material canonical layout pages (list-detail, supporting pane, feed) and fold-posture guidance page (developer.android.com .../foldables) returned 404/not retrieved.
- Actual dp dimensions and density of the Find N5 inner/cover displays not published in sources found.

## 4. Android platform: edge-to-edge, predictive back, photo access, background transfer, Sharesheet, haptics

### Takeaway
Target SDK 36: edge-to-edge and predictive back are mandatory, orientation locks are ignored on the Find N5 inner screen. Use the system photo picker (no permission) for importing, but if you scan MediaStore for camera-received files you must handle partial access (READ_MEDIA_VISUAL_USER_SELECTED). Receiving camera transfers in the background needs a correctly typed foreground service; dataSync has a 6h/24h limit.

### Cited Findings
- Edge-to-edge is enforced when targeting SDK 35 on Android 15+. Android 16: opt-out attribute `windowOptOutEdgeToEdgeEnforcement` is deprecated and disabled for apps targeting 36. Handle insets for system bars, display cutout, and gesture insets; keep scrolling content visible behind nav bar with clipToPadding=false pattern. — [Edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge); [Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16)
- Predictive back: for apps targeting 36 on Android 16+, system back animations (back-to-home, cross-task, cross-activity) are on by default; `onBackPressed` is not called and KEYCODE_BACK is not dispatched. Opt out per app/activity with `android:enableOnBackInvokedCallback="false"`. Callbacks with default priority disable the system animation. — [Predictive back](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture); [Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16)
- Photo picker: gives access to only selected media without permissions; `PickMultipleVisualMedia(max)` with a platform limit from `MediaStore.getPickImagesMaxLimit()`; available on Android 11+ with Google system updates (backport for 4.4 to 10 via Play services); `PickVisualMedia` opens half-screen; access lasts until restart/app stop unless `takePersistableUriPermission` (max 5,000 grants). — [Photo picker](https://developer.android.com/training/data-storage/shared/photopicker)
- Partial media access (Android 14): users can grant selected photos only. Manifest should declare `READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO` and `READ_MEDIA_VISUAL_USER_SELECTED`; request them in one operation (with `ACCESS_MEDIA_LOCATION` if needed); never persist permission state; re-query MediaStore on resume; treat URI access as temporary; offer UI to let user grant more. Apps only adding files to MediaStore need no storage permission on Android 10+. — [Partial photo and video access](https://developer.android.com/about/versions/14/changes/partial-photo-video-access)
- Android 16 / API 36: when a user limits access, photos owned by the app are pre-selected in the picker. — [Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16)
- Foreground service types: `connectedDevice` (requires Bluetooth/NFC/USB/network-state permission; Google suggests Companion Device Manager for continuous transfer to an external device); `dataSync` (no runtime prerequisites; subject to 6 hours per 24 hours since Android 15; cannot be launched from BOOT_COMPLETED); `mediaProcessing` (also 6h/24h); `shortService` ~3 minutes; Play Console declaration required. After the limit the system calls `onTimeout()`; app has a few seconds to `stopSelf()` or it crashes; timer resets when the user brings the app to the foreground. Starting a dataSync/mediaProcessing FGS from direct user interaction gives full 6h. — [FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types); [FGS timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout)
- Android 16 Local Network Permission (opt-in phase now; will be enforced in a later release): LAN TCP/UDP traffic will need the `NEARBY_WIFI_DEVICES` permission. — [Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16)
- Sharesheet: use `Intent.createChooser`; do not build your own share-target list; for multiple images use `ACTION_SEND_MULTIPLE` with `EXTRA_STREAM` list of content URIs (FileProvider or MediaStore) and `image/*` or `image/jpg`; grant read permission; Sharesheet previews depend on MIME type; Android 14+ supports custom actions (`ChooserAction`); `EXTRA_EXCLUDE_COMPONENTS` can hide your own targets. — [Sharesheet / send](https://developer.android.com/training/sharing/send)
- Haptics: prefer `View.performHapticFeedback` with `HapticFeedbackConstants` (no VIBRATE permission, respects user settings); `CONFIRM` is a short light vibration, `REJECT` stronger; discouraged: `createOneShot`/`createWaveform`. — [Haptic feedback](https://developer.android.com/develop/ui/views/haptics/haptic-feedback)

### Inferences
- The camera-to-phone transfer path (Sony A7R V / X-T50 over Wi-Fi/USB/Bluetooth) is the most platform-risky part. If transfer is initiated while the user has the app open, a `connectedDevice` or `dataSync` FGS started from the foreground gets a full window; for long batches of RAW files, plan a WorkManager/data-transfer-options fallback and implement `onTimeout()`. Which type fits depends on the exact transport; Play review requires justification (verify with Play policy).
- If camera transfer is over local Wi-Fi (PTP/IP or the camera's own AP), watch the Local Network Permission change (`NEARBY_WIFI_DEVICES`) before it becomes enforced.
- Import UX: for photos the app writes itself, no read permission is needed. For "show me what just arrived from the camera", the app owns its files in its own storage; use the photo picker only for user-selected library imports. Save to album = MediaStore insert (no permission on Android 10+).
- Haptics for sliders: use `SEGMENT_TICK` / `GESTURE_*`-style constants at detents (from my general knowledge of the HapticFeedbackConstants set; constants not verified in the fetched excerpt), and `CONFIRM` on batch-complete. Flutter's `HapticFeedback` maps to a subset; platform channel for finer constants.
- WeChat share: Sharesheet with `ACTION_SEND_MULTIPLE` is the standard route; WeChat's Moments multi-image limits (9 images) and WeChat SDK behavior are outside this research. Not verified.

### Gaps
- Exact API-level availability of individual haptic constants and the Flutter bridge for them not verified.
- WeChat Moments intent/SDK behavior (image count, compression, "original" quality) not researched here.
- Notification channel/ongoing-notification guidance for the FGS (POST_NOTIFICATIONS on Android 13+, progress notification style) not fetched.

## 5. Flutter specifics: Material 3, Cupertino, adaptive design, platform feel

### Takeaway
Flutter's adaptive docs prescribe Abstract / Measure / Branch. Material and Cupertino are now separate packages (`material_ui`, `cupertino_ui`), and Expressive is not shipped in-framework; use own components for the Dapple look with Material/Cupertino as behavior base.

### Cited Findings
- Three steps: Abstract (shared data for nav destinations), Measure (`MediaQuery.sizeOf` for window, `LayoutBuilder` for local constraints), Branch (switch UI on window size, not device type). Prefer `sizeOf` over `of` for rebuild efficiency. — [Flutter adaptive design](https://docs.flutter.dev/ui/adaptive-responsive/general)
- Material and Cupertino were decoupled in August 2026 into `material_ui` and `cupertino_ui` 1.0.0; run `dart fix` to migrate imports; in-framework removal at a future date; M3 Expressive and Liquid Glass official implementations "underway" without dates. — [Flutter blog](https://flutter.dev/blog/decoupling-material-cupertino)
- Third-party Expressive packages exist on pub.dev (e.g. `material_3_expressive` 1.0.8 requiring Flutter >=3.38; `m3_expressive`; `m3e_floating_toolbar`); a 2025 statement said the Flutter team was not actively building Expressive — conflicting with the 2026 blog claim; I did not find a release confirming Expressive in `material_ui`. — [pub.dev material_3_expressive](https://pub.dev/documentation/material_3_expressive/1.0.8/); [M3E Floating Toolbar](https://pub.dev/documentation/m3e_floating_toolbar/latest/); [Flutter blog](https://flutter.dev/blog/decoupling-material-cupertino)
- Large-format input: Material 3 buttons/selectors handle many input states; custom widgets need extra work (mouse, stylus, keyboard). — [Flutter large screens](https://docs.flutter.dev/ui/adaptive-responsive/large-screens)

### Inferences
- Dapple should own its component layer (slider, tool strip, grid cell, compare control) on top of `widgets`, because the product look is HIG-primary and the photo canvas must be custom (GPU image rendering). Use Material only where platform-conventional (dialogs, snackbars, system sheets), and avoid depending on third-party Expressive packages for core UI (maintenance risk).
- Pin `material_ui` / `cupertino_ui` explicitly in pubspec to avoid breakage when in-framework copies are removed.
- Adaptive switch per platform: on Android use the Android system share sheet, photo picker, predictive-back; on iOS use the iOS share sheet and PHPicker. Both are reached via platform channels or plugins; the Flutter app layer should depend on an abstract "ImportSource / ShareService / Haptics" interface.

### Gaps
- Flutter's "Automatic platform adaptations" page and the codelab were not fetched. Flutter predictive-back support status (Android) not verified here.
- Whether Flutter 3.41/3.44 renders edge-to-edge by default or needs `SystemChrome.setEnabledSystemUIMode(edgeToEdge)` was not verified.

## 6. Requirements for Dapple (Android first; each with source)

1. Target SDK 36 and support edge-to-edge: draw the photo canvas/grid behind system bars, pad controls with system-bar, cutout, and gesture insets; do not use the opt-out. — [Edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge); [Android 16](https://developer.android.com/about/versions/16/behavior-changes-16)
2. Never lock orientation; the Find N5 inner screen (sw >= 600dp) ignores locks under targetSdk 36 anyway. Test portrait/landscape on the near-square inner display. — [Android 16](https://developer.android.com/about/versions/16/behavior-changes-16); [Flutter large screens](https://docs.flutter.dev/ui/adaptive-responsive/large-screens)
3. Drive layout from window width classes (<600, 600-839, 840-1199, 1200+) via `MediaQuery.sizeOf`/`LayoutBuilder`, never from a device-model or isTablet check. — [Window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
4. Measure the Find N5's real dp widths and set breakpoints with that data; design so both sides of the 840dp boundary look intentional. — [OPPO specs](https://www.oppo.com/en/smartphones/series-find-n/find-n5/specs) + inference
5. Navigation: bottom NavigationBar below 600dp, NavigationRail at >=600dp; full-screen edit destination hides global nav. — [Flutter adaptive](https://docs.flutter.dev/ui/adaptive-responsive/general)
6. Wide windows: library grid + detail/edit supporting pane (list-detail pattern); sliders in a side panel; compact: photo on top, sliders in a bottom area. — [Canonical layouts](https://m3.material.io/foundations/layout/canonical-layouts/list-detail); [Support different display sizes](https://developer.android.com/develop/ui/compose/layouts/adaptive/support-different-display-sizes)
7. Hoist and persist editing state (selection, current photo, slider values, zoom) so fold/unfold, rotation and multi-window do not lose work. — [Support different display sizes](https://developer.android.com/develop/ui/compose/layouts/adaptive/support-different-display-sizes); [Android 16](https://developer.android.com/about/versions/16/behavior-changes-16) (rotation causes more activity recreation)
8. Grid columns from `SliverGridDelegateWithMaxCrossAxisExtent` (window-width-based), not a fixed count. — [Flutter large screens](https://docs.flutter.dev/ui/adaptive-responsive/large-screens)
9. Handle 2-pane impracticality when height is compact (open foldable in landscape, medium width): fall back to single pane with overlay tools. — [Window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)
10. All interactive elements >= 48x48dp (slider thumbs, selection checkboxes, toolbar icons), even when visually smaller; text contrast >= 4.5:1, icons/non-text >= 3:1. — [Android accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility)
11. Use a fixed neutral light color scheme with a single accent; make dynamic color optional/off by default; check every custom color against the contrast thresholds. — contrast thresholds per #10; dynamic-color decision is my inference
12. Opt in to predictive back with proper back callbacks (selection mode -> exit selection first, then edit -> library); do not keep a default-priority callback enabled when it is not needed, since it disables the system animation. — [Predictive back](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture)
13. Import from the library via the system photo picker (`PickMultipleVisualMedia`, image-only); no storage permission; persist URI access if processing continues after the app is backgrounded. — [Photo picker](https://developer.android.com/training/data-storage/shared/photopicker)
14. If the app must browse MediaStore, declare and request `READ_MEDIA_IMAGES` + `READ_MEDIA_VISUAL_USER_SELECTED` together, never cache permission state, re-query on resume, and provide a "select more photos" entry. — [Partial access](https://developer.android.com/about/versions/14/changes/partial-photo-video-access)
15. Save-to-album through MediaStore insert without requesting read permission. — [Partial access](https://developer.android.com/about/versions/14/changes/partial-photo-video-access)
16. Camera transfer reception: start the foreground service from a user action (so the 6h dataSync window applies fully), declare the correct FGS type (`connectedDevice` if BT/USB/network-state prerequisites fit, else `dataSync`) in manifest and Play Console, implement `onTimeout()` with `stopSelf()` and resumable transfers. — [FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types); [FGS timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout)
17. Consider Companion Device Manager for persistent camera pairing/presence instead of an always-on service. — [FGS types, connectedDevice alternatives](https://developer.android.com/develop/background-work/services/fgs/service-types)
18. Plan for the Android 16 Local Network Permission (`NEARBY_WIFI_DEVICES`) if the camera link is Wi-Fi/LAN; show a pre-permission explanation screen. — [Android 16](https://developer.android.com/about/versions/16/behavior-changes-16)
19. Share via the system Sharesheet only (`ACTION_SEND_MULTIPLE`, `image/*`, FileProvider URIs, read-grant flag); no in-app custom share list except possibly one "WeChat" quick action via `EXTRA_INITIAL_INTENTS` or Android 14 `ChooserAction`. Use `EXTRA_CHOOSER_RESULT` callback to learn the chosen target. — [Sharesheet](https://developer.android.com/training/sharing/send)
20. Review step: multi-select grid with long-press to enter selection mode, contextual top bar with "N selected", select-all, and primary action "Share"; snackbar with Undo for reject/remove; show per-photo develop state. — M3 pattern (component page not retrieved) + Google Photos precedent: [9to5Google](https://9to5google.com/2025/09/05/google-photos-editor-redesign-android/)
21. Edit screen: keep auto-develop result as the starting point, with 1 to 3 persistent sliders visible; avoid the tap-in/tap-out slider pattern users criticized; press-and-hold to compare with original. — [Android Central](https://www.androidcentral.com/apps-software/users-dreading-google-photos-less-functional-editor-updates-report); [9to5Google](https://9to5google.com/2025/09/05/google-photos-editor-redesign-android/)

## 7. HIG vs Material reconciliation (cross-platform Flutter)

All items below are my synthesis. HIG details were not researched in this note (another researcher covers HIG); only the Material/Android side is cited.

- Agree: both prefer content-first, edge-to-edge canvases (Android now enforces it — [Edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge)); both use system share sheets and system photo pickers for privacy-preserving access; both support press-and-hold-to-compare in photo editors; both want adaptive layouts driven by available space rather than device type.
- Differ in navigation: Android size classes switch bottom bar -> rail at 600dp ([Flutter adaptive](https://docs.flutter.dev/ui/adaptive-responsive/general)); iOS uses tab bar -> sidebar adaptivity on iPad. Reconcile: one shared destination list, rendered as bottom bar on compact and rail/sidebar on wider, styled in Dapple's own flat light look.
- Differ in back handling: Android has a system back gesture with predictive animation ([Predictive back](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture)); iOS uses edge-swipe pop and explicit back buttons. Reconcile: one navigation stack, with Android system back wired to it and iOS swipe-back from the same stack; keep an in-UI back/close control on edit screens for both.
- Differ in controls and motion: Material Expressive favors springy, shape-morphing components and button groups; HIG favors restrained, system-feel controls. Reconcile: custom Dapple controls with one shared, subdued motion language (spring easing with low overshoot), keeping platform-native pieces (dialogs, pickers, share sheets, haptics) native so the "feel" adapts per platform. Since HIG is the primary basis, default to HIG-like visual restraint and use Material semantics only for behavior (48dp targets, insets, back, FGS notifications).
- Differ in touch targets: Android 48dp ([accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility)) vs HIG 44pt; use 48dp as the shared minimum so one layout satisfies both.
- Differ in color: Material's dynamic color vs iOS fixed system palettes; for Dapple use a fixed neutral palette on both (see requirement 11).
- Foldable/large-screen: Android-only concern for now (Find N5), but the same window-width logic carries to iPad later; do not hard-code Android class names.
